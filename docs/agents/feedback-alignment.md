# 反馈对齐与输入规范

> 用户（维护者）反馈 → agent 实现 之间的对称确认协议。目的：拆票前消灭「静默误读」，交付后消灭「静默丢弃」。配套：[缺陷流程](./defect-workflow.md)、[UI 反馈四要素](./ui-feedback.md)、[质量门禁](./quality-gates.md)（QG-10、DQ-9）。
> 2026-11-18 经维护者裁定生效：①对账表强制；②禁止静默丢弃；③回复约定「全按默认 + 指定改哪条」。

## 一、为什么（实证）

editor-surface-batch21：20 票交付，8 票被重开（首验通过率 60%）；加 doc-property-refine 2 票、batch20 1 票、既有 2 票，共 13 张重做 + 1 张待真机（#903）。按主因：

| 主因 | 票 | 一句话机制 |
|---|---|---|
| 需求语义误读 | #1044 #1049 #1054 #1055 #1050(徽标) | 双控件/单面板、工具条时机、复用语义、图标 vs 文字、标识设计 |
| 验收口径错 | #1053 #1057 | 断言测代理属性（text-overflow / sticky），可见真相来自另一属性 |
| 面×状态覆盖缺失 | #1051 #1056 #1016 #1050(分支) (#903) | 漏悬浮预览面、漏表格等构造、全局活动视图写错格、漏预览态分支 |
| 状态空间缺失 | #1034 #1019 #1055(焦点) | 不测重启、不测光标在隐藏区、不测动作后焦点 |
| 既有缺陷 | #1012 (#1016 #903) | md-bundle 移植带入 |

13 张重做中纯逻辑写错仅 1 张（#1012 输入配对）。**缺陷主体是验证设计与对齐缺失，不是编码能力。** 措施总账见文末附录。

## 二、对账表（强制）

batch 级反馈（多条一起提）在拆票前必须产出一张对账表：

| # | 用户原话 | agent 理解（行为化复述） | 歧义点/候选（★=默认） | 处置 |
|---|---|---|---|---|
| 1 | 页签间距加宽一个指针 | 16→32px | ★+16px（另一解 ×2） | 做票 |
| 2 | 徽标显示回车 | 回车图标（svg + aria-label） | ★图标（另一解：文字「回车」） | 做票 |
| 3 | （信息不足的条目） | —— | 需要截图才能定验收 | **待补充** |
| 4 | （与现行规格冲突） | —— | 建议走 Δ-change | **暂缓 + 理由** |

三条硬规则（裁定 2026-11-18）：

1. **强制**：batch 级反馈未经对账确认不得拆票。单条小缺陷可并入下一批对账，不强制单独一轮。
2. **禁止静默丢弃**：每一条编号反馈必须出现在表里；不做/暂缓必须写理由。处置列是用户核查漏网的唯一入口。
3. **回复约定**：候选全部带默认；用户回复「全按默认，#N 选 B，#M 补充：……」即完成一轮，成本一句话。

歧义候选给 2–3 个并标默认；交互形态争议（图标样式/面板结构/时机）出对比稿再裁，不靠文字猜。确认后 G0-PRE 把对账表固化进 spec issue；OQ（Open Questions）只留真开放问题。

## 三、何时用 /grill-me（升级路径，默认不用）

- **默认不用**：对账表的瓶颈是用户时间；grill-me 多轮追问把负担翻回用户，与回复约定相反。要治的病是「静默误读」，解药是复述+候选+处置列，不是加大提问量。
- **升级条件**：开放型新需求（非缺陷/优化），2–3 个候选形不成收敛（形态/交互模型未定，如「datetime 单面板」的面板结构）→ 限**一次 3–5 问**的 grill 轮把缺的决策问出来，随后回对账表。
- **缺陷不做 grill**：triage 走证据复现，不走访谈。
- 用户主动说「grill 我」随时触发（该 skill 自带触发词）。

## 四、一起提还是分开提（归并规则）

**按条目组织，不按消息组织。**

- 一条消息混需求/优化/缺陷：可以且推荐。同模块的一起提共享上下文、对账一次成表，避免顺序歧义（后面的缺陷被当成前面需求的修正）。
- 每条**编号并标类别**（缺陷/优化/需求）。类别标错没关系，对账表会纠正路由：需求/优化 → change 线（规格增量）；缺陷 → 缺陷线（triage→红→修）。
- 不同模块混一条消息也可以，按条目归并。
- **唯一必须立即单独提的：阻断性缺陷**（核心流程坏、阻塞继续测试），不等凑批。
- 频率：攒自然批次（测完一轮）最好，不一条一条发。（夜间节奏与验收点安排见 §七）

## 五、写法指南（怎么写 agent 理解得更准）

先兜底：**允许糙写**，对齐轮就是为糙输入设计的——写得糙没关系，跳过对齐轮才有风险。以下规律来自本轮真实票：

| 表述方式 | agent 容易偏到哪 | 建议写法 |
|---|---|---|
| 只说不要什么：「不要省略号」 | 解法空间大（缩小/换行/滚动/全显），默认常不中 | **正向描述终态**：「名称完整显示，放不下时页签条横向滚动」 |
| 引号内的词被当字面量：「徽标『回车』」 | 做成两个字的文本，用户要的是图标 | 要图标写「图标」；要文字才加引号 |
| 时机+位置混一句：「落点跟随显示」 | 各答对一半 | **拆开**：何时出现 / 出现在哪 / 何时消失 |
| 判断词：「最方便」「好看」「舒服」 | 无法换算成实现 | 给参照物：「像系统日历那样」「上一版那样」——参照 > 形容词 |
| 比喻单位：「加宽一个指针」 | 需换算回读确认 | 有数给数（「再宽 16px」），没有就等换算确认 |
| 一段塞多件事 | 漏接 | 一行一条、编号、标类别 |
| 总结式缺陷报告：「都没有实现」 | 只能按代码面盲查 | **三要素**：现象（+截图最好）/ 期望 / 复现路径 |
| 同音口误：「不要行号显示」 | 猜+确认（本轮猜对） | 关键名词写完扫一眼 |

- **截图是最高带宽的输入**：现象一眼定位到面。
- 引用界面元素用可见名字（「顶栏右侧的 ×」），不必学开发术语。
- 轻量模板（可抄，不强制——对账表会补缺口）：

```
[缺陷/优化/需求] 一句话标题
现象：…（截图更好）
期望：…（何时/何地/什么内容）
路径：…（缺陷必填）
```

## 六、与既有流程的衔接

- **G0-PRE**：对账表固化进 spec issue；用户反馈与锚点冲突时走 Δ-change（DQ-9 反模式）。
- **视觉类反馈**：四要素与候选终态见 [ui-feedback.md](./ui-feedback.md)；对账表负责覆盖与复述，四要素负责候选的具体化。
- **缺陷线**：triage / DQ-1..DQ-9 见 [defect-workflow.md](./defect-workflow.md)。
- **验证侧**：断言审计与反事实复跑见 [quality-gates.md](./quality-gates.md) QG-10；真机偏差分级见 DQ-9。

## 七、夜跑晨验节奏（2026-11-18 裁定）

用户晚间提交、夜里由 agent 跑批、白天验收——验收点从「每批一次」收敛到「每早一次」，夜里连续跑，不停等验收。

- **每晚总量 ≤8 票**：＝一个上午能实测的量；超出的票排次晚（已对账、已入看板，不会丢）。
- **实施顺序 = 语义风险倒序**：最新颖/最依赖用户裁定的票先做（校准样本），低风险缺陷修复随后。晨验先验前几票，发现理解偏差后，未开工的票按修正后的理解继续——拦住未实施的比重做已实施的便宜。
- **未确认不实施**：对账表未经用户确认的票，夜里降级为「诊断之夜」——只做 triage（复现/根因/红证据/triage brief 贴票），不写实现；用户晨间确认后次晚实施。
- **晨报验收卡**（每早一份）：本晚交付清单（功能语言）+ 每票待验收项 + 截图证据 + 「建议优先实测」标注（语义风险高的票）。
- 配套纪律不变：全量对账不丢弃、全量拆票入库、每票独立 PR 可回退、重做走前置修正票；DQ-9/QG-10 门禁不放松。
- 节奏跟随提交与确认时间，不强制白天/夜晚；白天提交且确认后同样即时实施。
