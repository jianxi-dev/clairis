# 反馈对齐与输入规范

> 用户（维护者）反馈 → agent 实现 之间的对称确认协议。目的：拆票前消灭「静默误读」，交付后消灭「静默丢弃」。配套：[缺陷流程](./defect-workflow.md)、[UI 反馈四要素](./ui-feedback.md)、[质量门禁](./quality-gates.md)（QG-10、DQ-9）。
> 2026-11-18 经维护者裁定生效：①对账表强制；②禁止静默丢弃；③回复约定「全按默认 + 指定改哪条」。
> 2026-11-22 扩展：新需求/优化线在 G0-PRE 1a 同样强制对账（触发信号与豁免见 §二），`cw-tickets-check.sh` C11 机检 spec issue 的 `## 输入对账` 段。
> 2026-11-23 优化（维护者裁定）：对账表加「功能模块」列、按模块归组排序，并新增「冲突/疑点」列与综合分析义务——提出人自己的多条内容之间、以及内容与系统现状之间出现矛盾时，必须在表内显式反馈，不得静默按某一支实现（见 §二）。

## 二、对账表（强制）

batch 级反馈（多条一起提）与命中触发信号的单条新需求/优化，在拆票前必须产出一张对账表：

| #   | 功能模块 | 用户原话               | agent 理解（行为化复述）     |     歧义点/候选（★=默认）     | 冲突/疑点                                                                                 | 处置            |
| --- | -------- | ---------------------- | ---------------------------- | :---------------------------: | ----------------------------------------------------------------------------------------- | --------------- |
| 1   | 页签     | 页签间距加宽一个指针   | 16→32px                      |      ★+16px（另一解 ×2）      | —                                                                                         | 做票            |
| 2   | 页签     | 页签上要显示回车键提示 | 页签标题后叠一个回车小图标   | ★图标（另一解：文字「回车」） | 与 #3「页签只留纯文本、不加装饰」冲突                                                     | **需你裁决**    |
| 3   | 页签     | 页签不要任何附加标识   | 页签只显示标题文本           |        ★去掉图标与徽标        | 见 #2                                                                                     | **待确认**      |
| 4   | 块手柄   | 徽标显示回车           | 回车图标（svg + aria-label） | ★图标（另一解：文字「回车」） | —                                                                                         | 做票            |
| 5   | 附件卡   | 附件卡片能调宽度       | docx 卡片宽度可调            | ★对齐+宽度（另一解：仅对齐）  | 与现行规格不符：`openspec/specs/attachment-card/spec.md` 已定「卡片宽度固定跟随正文列宽」 | **走 Δ-change** |
| 6   | 附件卡   | （信息不足的条目）     | ——                           |      需要截图才能定验收       | —                                                                                         | **待确认**      |

### 列定义

| 列          | 写法                                                                                                                                                                                                                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 功能模块    | 用户可见功能域的名词，不写文件路径、不写组件名：`页签` `顶栏` `块手柄` `图片` `附件卡` `表格` `高亮` `菜单` `设置` `快速捕获`；无 UI 面用 `基础设施` / `文档`。取值须能在 `CONTEXT.md` 或 `.opencode/project-tree.md` 找到对应概念，同一 change 内同名同写（不写「页签」又写「tab」） |
| 用户原话    | 逐字照抄，不改写不省略；一条 = 一个编号                                                                                                                                                                                                                                               |
| agent 理解  | 行为化复述（谁在什么界面、什么时机、看到什么），不写实现方案                                                                                                                                                                                                                          |
| 歧义点/候选 | 2–3 个候选，★ 标默认；歧义是「选择题」                                                                                                                                                                                                                                                |
| 冲突/疑点   | 无则填 `—`；有则写**冲突对象 + 依据**（`与 #M 冲突：…` / `与 <规格路径> §N 不符` / `核对证据 src/a.ts:123`）。冲突是「裁决题」                                                                                                                                                        |
| 处置        | 枚举：`做票` / `暂缓 + 理由` / `待确认` / `需你裁决` / `走 Δ-change`。`待确认` 与 `需你裁决` = 未完成对账（不得拆票）；`走 Δ-change` = 该条不进本 change，冲突列必须带符合依据                                                                                                        |

### 排序规则（相同模块排在一起）

1. 先按功能模块归组，同模块的行必须**连续**（不允许 `页签 → 块手柄 → 页签` 这样散开）。
2. 模块组之间按「该模块首个条目的原始编号」升序——归组但不打乱用户书写顺序的模块先后。
3. 组内按原始 `#` 升序；`#` 保留用户提交顺序不得重排（冲突行靠 `#` 互指，重排会使引用失效）。
4. 归组后若发现原本分开的两条其实是同一件事 → 合并成一条并在处置列写 `与 #M 合并`。

### 综合分析（排库比对，必做不可跳过）

逐条把用户内容与**系统现状**比对，四个对照面缺一不可：

| 对照面              | 位置                                                            | 用来发现                                   |
| ------------------- | --------------------------------------------------------------- | ------------------------------------------ |
| 功能规格            | `openspec/specs/`                                               | 与已定规格不符（→ Δ-change，不静默改规格） |
| 批准设计 + 设计系统 | `docs/design/approved/`、`docs/design/system/spec.md`           | 与已批准视觉/交互裁决不符                  |
| 现有实现            | 相关源码（给 `path:line`）；必要时 `npm run tauri dev` 真机核对 | 用户说「没有/坏了」但现状已有，或反之      |
| 同批其他条目        | 本表其他行                                                      | 条目间互相矛盾（同一控件两种终态要求）     |

四条冲突判据与落点：

| 冲突类型       | 判据                                    | 冲突列写什么                      | 处置默认                            |
| -------------- | --------------------------------------- | --------------------------------- | ----------------------------------- |
| 条目间冲突     | A 要求 X，B 要求非 X（同一控件/同一面） | `与 #M 冲突：<一句话机制>`        | `需你裁决`                          |
| 与现行规格冲突 | 与 spec / 批准设计条款不符              | `与 <路径> §N 不符：<差异>`       | `走 Δ-change`                       |
| 与现状不符     | 与代码/真机实际行为不符                 | `核对证据 <path:line>（实际已…）` | `做票（改为微调）` 或 `暂缓 + 理由` |
| 条目内部矛盾   | 同一句里前后口径不一、单位与数值打架    | 歧义列给候选，冲突列写矛盾点      | `待确认`                            |

**反馈纪律**：冲突一律写在表里反馈，不在实现时二选一硬做。`需你裁决` 行必须在表尾确认行被点名（`确认：#2 选 A`），未点名即视同未确认；`走 Δ-change` 行也要在确认行点名路线（例：`确认：#5 走 Δ-change`）。用户可能同时提出互相矛盾的两条，也可能描述了系统早已具备的行为——这两种情况都不是「用户错」，是必须先对齐的输入缺陷。

**固化位置**：整表作为 spec issue 的一条评论发布，标题固定为 `## 输入对账`，表头固定七列且顺序不变（`# | 功能模块 | 用户原话 | agent 理解（行为化复述） | 歧义点/候选（★=默认） | 冲突/疑点 | 处置`）；表尾写一行用户确认：`确认：全按默认，#2 选 A`。C11 按此结构机检：段存在、七列、功能模块与处置列非空、同模块行连续、无 `待确认`/`需你裁决`、暂缓须带理由、有 `确认：` 行（只查结构，不判语义）。五列旧表仅对 2026-11-23 前已建的对账表兼容放行，新 change 一律七列。

### 触发与豁免（2026-11-22 扩至新需求/优化线）

**必须对账**：

- batch：≥2 条一起提（沿用原规则）。
- 单条新需求/优化，命中任一信号：形态/交互模型未定（面板结构、单双控件、出现时机）；新增用户可见面；无一手原型且无规范锚点；含判断词（「最方便 / 好看 / 舒服 / 差不多」）；跨面组合改动（一个需求同时改编辑面与外壳）。

**可豁免**（在 spec issue 留一行 `输入对账豁免: <理由>`，C11 认这一行）：

- `no-ui-impact` 的纯重构 / 纯文档 / 纯基建；
- 输入是逐字一手规格（规范条款、设计稿、用户已逐条给出验收标准），且不含判断词、无形态未定；
- 缺陷条目（缺陷线由 triage 证据复现兜底，走 DQ-1..DQ-3，不走对账）。

**未确认不拆票**：处置列写 `待确认` 即未完成对账；允许出 proposal/design/tasks 草稿，禁止拆票与实施（与 §七「未确认不实施」同一纪律）。

四条硬规则（1–3 裁定 2026-11-18，4 裁定 2026-11-23）：

1. **强制**：batch 级反馈与命中触发信号的单条需求/优化，未经对账确认不得拆票。未命中信号的单条小缺陷可并入下一批对账，不强制单独一轮。
2. **禁止静默丢弃**：每一条编号反馈必须出现在表里；不做/暂缓必须写理由。处置列是用户核查漏网的唯一入口。
3. **回复约定**：候选全部带默认；用户回复「全按默认，#N 选 B，#M 补充：……」即完成一轮，成本一句话。
4. **禁止静默消化冲突**：条目间矛盾、与现行规格矛盾、与现状不符，都必须落在「冲突/疑点」列并反馈给用户裁决；不得在实现阶段挑一支偷偷做掉，也不得把它降级成「歧义候选」当成普通选择题。

歧义候选给 2–3 个并标默认；交互形态争议（图标样式/面板结构/时机）出对比稿再裁，不靠文字猜。确认后 G0-PRE 把对账表固化进 spec issue；OQ（Open Questions）只留真开放问题。

## 三、何时用 /grill-me（升级路径，默认不用）

- **默认不用**：对账表的瓶颈是用户时间；grill-me 多轮追问把负担翻回用户，与回复约定相反。要治的病是「静默误读」，解药是复述+候选+处置列，不是加大提问量。
- **升级条件**：开放型新需求（非缺陷/优化），2–3 个候选形不成收敛（形态/交互模型未定，如「datetime 单面板」的面板结构）→ 限**一次 3–5 问**的 grill 轮把缺的决策问出来，随后回对账表。
- **缺陷不做 grill**：triage 走证据复现，不走访谈。
- 用户主动说「grill 我」随时触发（该 skill 自带触发词）。

## 四、一起提还是分开提（归并规则）

**按条目组织，不按消息组织。**

- 一条消息混需求/优化/缺陷：可以且推荐。同模块的一起提共享上下文、对账一次成表，避免顺序歧义（后面的缺陷被当成前面需求的修正）。
- 每条**编号并标类别**（缺陷/优化/需求）。类别标错没关系，对账表会纠正路由：需求/优化 → change 线（规格增量）；缺陷 → 缺陷线（triage→红→修）。
- 不同模块混一条消息也可以，按条目归并。
- **唯一必须立即单独提的：阻断性缺陷**（核心流程坏、阻塞继续测试），不等凑批。
- 频率：攒自然批次（测完一轮）最好，不一条一条发。（夜间节奏与验收点安排见 §七）

## 五、写法指南（怎么写 agent 理解得更准）

先兜底：**允许糙写**，对齐轮就是为糙输入设计的——写得糙没关系，跳过对齐轮才有风险。以下规律来自本轮真实票：

| 表述方式 | agent 容易偏到哪 | 建议写法 |
|---|---|---|
| 只说不要什么：「不要省略号」 | 解法空间大（缩小/换行/滚动/全显），默认常不中 | **正向描述终态**：「名称完整显示，放不下时页签条横向滚动」 |
| 引号内的词被当字面量：「徽标『回车』」 | 做成两个字的文本，用户要的是图标 | 要图标写「图标」；要文字才加引号 |
| 时机+位置混一句：「落点跟随显示」 | 各答对一半 | **拆开**：何时出现 / 出现在哪 / 何时消失 |
| 判断词：「最方便」「好看」「舒服」 | 无法换算成实现 | 给参照物：「像系统日历那样」「上一版那样」——参照 > 形容词 |
| 比喻单位：「加宽一个指针」 | 需换算回读确认 | 有数给数（「再宽 16px」），没有就等换算确认 |
| 一段塞多件事 | 漏接 | 一行一条、编号、标类别 |
| 总结式缺陷报告：「都没有实现」 | 只能按代码面盲查 | **三要素**：现象（+截图最好）/ 期望 / 复现路径 |
| 同音口误：「不要行号显示」 | 猜+确认（本轮猜对） | 关键名词写完扫一眼 |

- **截图是最高带宽的输入**：现象一眼定位到面。
- 引用界面元素用可见名字（「顶栏右侧的 ×」），不必学开发术语。
- 轻量模板（可抄，不强制——对账表会补缺口）：

```
[缺陷/优化/需求] 一句话标题
现象：…（截图更好）
期望：…（何时/何地/什么内容）
路径：…（缺陷必填）
```

## 六、与既有流程的衔接

- **G0-PRE 1a**：对账表（或 `输入对账豁免: <理由>` 一行）固化进 spec issue 的 `## 输入对账` 评论；表内已按功能模块归组，且已跑完 §二「综合分析」四面对照；C11 机检结构，不合格不得进入 1b/阶段二；用户反馈与锚点冲突时走 Δ-change（DQ-9 反模式）。
- **票面**：功能模块列同时决定任务分组——`tasks.md` 的 task 分组与对账表模块归组保持一致，便于按模块验收。
- **视觉类反馈**：四要素与候选终态见 [ui-feedback.md](./ui-feedback.md)；对账表负责覆盖与复述，四要素负责候选的具体化。
- **缺陷线**：triage / DQ-1..DQ-9 见 [defect-workflow.md](./defect-workflow.md)。
- **验证侧**：断言审计与反事实复跑见 [quality-gates.md](./quality-gates.md) QG-10；真机偏差分级见 DQ-9。

## 七、夜跑晨验节奏（2026-11-18 裁定）

用户晚间提交、夜里由 agent 跑批、白天验收——验收点从「每批一次」收敛到「每早一次」，夜里连续跑，不停等验收。

- **每晚总量 ≤8 票**：＝一个上午能实测的量；超出的票排次晚（已对账、已入看板，不会丢）。
- **实施顺序 = 语义风险倒序**：最新颖/最依赖用户裁定的票先做（校准样本），低风险缺陷修复随后。晨验先验前几票，发现理解偏差后，未开工的票按修正后的理解继续——拦住未实施的比重做已实施的便宜。
- **未确认不实施**：对账表未经用户确认的票，夜里降级为「诊断之夜」——只做 triage（复现/根因/红证据/triage brief 贴票），不写实现；用户晨间确认后次晚实施。
- **晨报验收卡**（每早一份）：本晚交付清单（功能语言）+ 每票待验收项 + 截图证据 + 「建议优先实测」标注（语义风险高的票）。
- 配套纪律不变：全量对账不丢弃、全量拆票入库、每票独立 PR 可回退、重做走前置修正票；DQ-9/QG-10 门禁不放松。
- 节奏跟随提交与确认时间，不强制白天/夜晚；白天提交且确认后同样即时实施。
