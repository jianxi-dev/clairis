# 事故复盘：#1678 裁剪视口抖动——约 40 轮返修的经验

> 适用：所有「点击/滚动位置被意外改动」类缺陷（裁剪、图片、模式切换、选区）
> 最后更新：2026-11-28
> 关联：#1603（图片工具批次）、#1678（本事故）、PR #1694→#1734

## 事故概述

#1603/#1678 的「裁剪首抖、多图下跳、预览↔编辑错位、点正文跳走并选中一片」，
累计约 40 次提交、18 轮真机返修才收敛。期间多次出现「本地全绿、真机仍抖」
「修好了又回退」「同一现象换三个方向都不生效」。

**最终根因只有一条**：`suppressCaret` 的放行列表包含 `[contenteditable='true']`，
而 **CM6 正文本身就是 contenteditable** —— 拦截函数在判断放行时第一行就 `return`，
**整个拦截逻辑从未执行过一次**。

在此之前的所有调整（把监听从 document 挪到 window、补 pointerdown、
加 pinScroll、加高度锁定、加光标复位……）都在一个不会运行的代码路径上
或在其下游做补救。

## 为什么走了这么远（八类弯路，每条都可复用）

### 1. 门禁代码未验证「是否真的执行」
拦截写好了、类型检查过了、e2e 也过（因为 e2e 场景不触发），但从没确认它
**实际被调用**。放行条件里的 `[contenteditable='true']` 静默吞掉了所有点击。

> **教训**：任何拦截/守卫/门禁，落地时先证明它执行过——加 DEV 计数器或一次性
> 日志，看到「进入拦截」再谈效果。`if (shouldSkip) return;` 这类早退是最高危写法。

### 2. 拿 headless 绿灯当「修好了」
抖动与高度变化在 Chromium 完全不复现（`scrollHeight 1721 → 1721`），
每次本地全绿、真机照旧。

> **教训**：平台差异类问题（WKWebView / 原生控件 / 字体度量）**只能以真机日志
> 为准**。e2e 在这种场景下只是防退化守卫，不能当验收证据；交付时必须写明
> 「本项需真机确认」。

### 3. 猜机制而不是先取证
前 6 轮在猜「blur 时序」「滚动锚定」「内容高度塌陷」。直到给
`cropJumpProbe` 加上 `JUMP{from,to,sel,docH,inputs}` 与 `MARK` 打点，
才在一条日志里看清：`sel 0→1348` 紧跟 `pointerdown:cm-line`，

> **教训**：现象有多个可能来源时，先加探针（滚动位置、selection、内容高度、
> 事件序列），用**数据分组**找规律（按 `from`/会话分组立刻暴露「第 2 张必现、
> 第 1 张偶发」）。没有日志的修复都是赌博。

### 4. 把「症状」当「机制」
「跳」至少有四个来源：
- 内容高度变化（**裁剪确认后的正常结果**，图 550→419）
- CM6 光标揭示滚动（**真根因**）
- 浏览器原生滚动锚定（`overflow-anchor`）
- `scrollTop` 被夹取（内容变矮时）

曾把「正常结果」当 bug 修（给图片锁高度），把「夹取」当主因（改像素恢复）。

> **教训**：先回答「谁改的、什么时候改的、改了多少」，再看要不要修。
> 一个现象里混着正常行为时，先把它从怀疑列表里划掉。

### 5. 事后回拉 vs 源头阻断
`pinScroll` / 会话守护都是「变了再拉回」。回拉粒度从 5 帧压到 1 帧，
用户依然看得见「上下抖一下」。

> **教训**：能阻断源头就不要补。判定标准：**用户是否能感知到中间态**——
> 能感知就说明补得不够，必须回到「谁在改」那一层。

### 6. 让位（rebase）条件过宽
滚动守护允许「拖框 pointerdown」让位；但**双击确认的第一下正好落在裁剪框上**，
于是守护把已被带偏的位置认作新基准，永久不再拉回（第 2 张每次必现 -400~-540）。

> **教训**：让位/豁免条件必须与「真正的用户意图」一一对应。**改变状态的操作用
> 事件本身判定不可靠**（双击、长按、组合手势），要用结果（位移阈值、是否拖动）
> 判定。

### 7. 长生命周期循环没有容错
守护里写了 `if (!scroller.isConnected) return;` → 首裁 widget 重建让 scroller
瞬态脱离，守护**永久退出**；后来又因在 CM6 更新周期内 `dispatch(selection)`
抛异常，异常直接终止 rAF 调度。

> **教训**：rAF/interval 守护必须 ①`try/catch` 包住每一步 ②瞬态条件不退出
> 而是继续重查 ③有明确的停止条件（会话结束）。否则一次异常等于永久失效。

### 8. 测试环境本身在骗人
多轮 e2e 跑在 1424 端口，而那个 dev server 属于**另一个 worktree**
（`clairis-auto-3` / `clairis-fix1652` / `clairis-base-check`），
测的根本不是当前代码。为此给 `playwright.config.ts` 加了 `PW_DEV_PORT`。

> **教训**：并行 worktree 下跑测试前确认 server 的 cwd（`lsof -p <pid> | grep cwd`）。
> 出现「改了代码测试结果不变」「日志里没有新加的探针」时，第一怀疑对象是
> **跑错了代码**。

## 最终修复（三条，缺一不可）

| 位置 | 作用 |
|---|---|
| `imageCrop.ts` `suppressCaret` 放行列表移除 `[contenteditable='true']` | **让拦截真正执行**（根因） |
| `suppressCaret` 对框外 `pointerdown/mousedown` 直接调 `onOutsideClick` + `preventDefault + stopPropagation` | 点框外确认提前到按下，CM6 收不到事件 |
| 会话级滚动守护（document capture + rAF 兜底 + try/catch） | 兜底任何漏网的 scrollTop 变化 |

验证结论：首图首裁、2 图、反复切换裁剪，视口零位移（真机确认）。

## 规则（MANDATORY）

1. **门禁可执行性**：新增拦截/守卫/白名单，必须先用 DEV 打点或计数器证明
   「代码被执行」，再谈效果；PR 描述里写明证明方式。
2. **早退列表要怀疑**：放行列表中出现宽泛选择器（`[contenteditable]`、
   `.cm-*`、`body *`）时视为高危，必须验证它不会吞掉目标场景。
3. **平台差异以真机为准**：WKWebView 特有行为（滚动锚定、光标揭示、字体度量）
   不得用 headless 结果当验收；e2e 仅作防退化守卫，交付说明里标注「需真机确认」。
4. **先探针后修复**：同一现象出现 ≥2 次未解决，停止改代码，先加探针
   （滚动位置 / selection / 内容高度 / 事件序列），用日志分组找规律。
5. **区分症状与机制**：修复前必须能回答「谁在什么时刻改了什么」；
   正常行为（如裁剪后图片变小）不得当 bug 修。
6. **守护循环三原则**：try/catch、瞬态不退出、明确停止条件。
7. **并行 worktree 测试纪律**：跑 e2e 前确认 dev server 的 cwd；
   本仓已支持 `PW_DEV_PORT=<port> npx playwright test`。

## 收尾检查单（同类缺陷交付前逐项确认）

- [ ] 拦截/守卫代码有执行证据（DEV 打点或一次性日志截图）
- [ ] 修复点能对应到日志里的具体字段（`sel` / `from→to` / `docH` / `inputs`）
- [ ] 正常行为已从怀疑列表排除（例如内容高度的正常变化）
- [ ] rAF/interval 守护有 try/catch 与停止条件
- [ ] e2e 覆盖：主路径 + 反复操作（≥3 轮）+ 边界（Esc / 点框外 / 多图）
- [ ] 交付说明写明「需真机确认」的部分
- [ ] 测试 server 的 cwd 与当前 worktree 一致
