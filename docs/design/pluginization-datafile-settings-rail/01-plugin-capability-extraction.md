# 插件化能力提取方案

> 状态：设计方案（已通过独立对抗评审，按意见修订）
> 对应目标：第 1 项——盘点本仓可提取为插件的能力清单与提取方案
> 事实基线：`src-tauri/src/extensions.rs`、`src/lib/capabilities.ts`、`src/ui/settings/SettingsView.tsx`、`src-tauri/src/commands/ai_agent.rs`、`docs/research/technical/data-fileization-omarchy-inventory.md`、`docs/agents/data-surface.md`

## 1. 背景与目标

本仓能力按 AGENTS.md 两个目标取向可提取为插件：① **独立控制、开发升级**——能力独立打包、独立加载、独立升级；② **能力复用与用户自定义**——用户可按需启用/停用、自定义扩展。

本方案回答：哪些能力可提取为插件、插件的形态与边界、加载/生命周期/权限设计，以及分批提取路线。

## 2. 插件形态定义（三类，互斥）

| 形态 | 结构 | 加载方式 | 适用 |
|---|---|---|---|
| **配置型插件** | 声明式数据（JSON/TOML/Markdown） | 加载时读入、映射到配置字段 | 纯数据可配置的能力 |
| **注册型插件** | 注册数据（manifest + JSON） | 加载时解析注册表 | 结构可增删、需校验的能力 |
| **技能型插件** | SKILL.md 驱动的 AGENT 能力包 | 注入 AGENT 上下文 | AI 能力 |

**术语统一**：目录名与文档统一用 **plugin**（不复用既有「extension」术语，避免混淆）。插件目录定为 `data/plugins/`（独立于 `user/`，用户层）。

## 4. 设计实现方案

### 4.1 插件目录结构

```
data/plugins/                     插件根（用户层，独立于 user/）
  <plugin-id>/
    manifest.json                 插件声明（字段名统一，见 §4.2）
    <data files>                  配置型/注册型插件的数据
    SKILL.md                      技能型插件的能力声明
```

### 4.2 manifest 字段统一（修正 P1）

**现状**：manifest 字段名在文档/示例/代码间不一致（`id`/`name`/`version` 等字段各文档写法不同）。

**设计**：统一 manifest 字段为：
- `id`（插件唯一标识）、`name`（显示名）、`version`、`type`（config/registry/skill）、`description`
- 注册型插件增补 `permissions`（声明所需权限，如 `filesystem`）

**权限声明（修正 P1 遗漏）**：扩展包内 JSON 当前**缺 `filesystem` 权限声明**（需在 `env.toml` 声明）。manifest 的 `permissions` 字段补上，加载时校验声明的权限是否在白名单内。

### 4.3 加载管线（修正 P1/P2）

**现状（校正）**：`extensions.rs` 是**同步一次性加载**，无热重载。方案原称的「加载期巡检、容错、热加载」与实际不符。

**设计**：
- **加载**：启动时同步扫描 `data/plugins/`，逐插件读 manifest、校验权限、解析数据 → 映射到配置/注册表/AGENT 上下文。
- **生命周期裁定（修正 P2）**：**以「重启生效」为主**，不承诺热加载。热加载需先建 watcher 基础设施（与第 2 项 §5.3 一致，`settings.json` 已有 watcher，但 `data/plugins/` 无）。**裁定**：插件改动重启生效，热加载列为后续，不在本批实现。
- **容错**：单个插件解析失败 → 跳过 + 告警，不影响其他插件与主应用（加载期巡检保留）。

### 4.4 SKILL.md 注入面（补充 P3 遗漏）

**现状（校正）**：`seed_skill_map` 已把 SKILL_MD 注入 AGENT 上下文，但方案此前未设计**注入面的拼装与边界**。

**设计**：
- **注入拼装**：AGENT 上下文构建时，聚合所有已启用技能型插件的 SKILL.md 内容（+ 内置 SKILL_MAP），拼装为 AGENT 的能力声明。
- **边界**：注入内容仅声明「AGENT 可做什么」，不引入可执行代码（技能型插件仍走 AGENT 调用，不直接执行用户代码）。
- **可见性**：与第 2 项 §5.5 的 SKILL_MAP 载体统一——插件体系管「哪些插件贡献 SKILL.md」，数据文件体系管「字段配置」，两者在技能型插件上协同。

### 4.5 配置载体与插件的维度划分（澄清 C5）

**裁定**：插件体系与数据文件化是**正交维度**，不重复：
- **数据文件化**管「配置值」——字段值存哪、怎么合并、怎么热应用。
- **插件化**管「打包/加载/升级」——能力如何独立打包、独立加载、独立升级、权限声明。

A 档能力（A3 主题、A4 扩展、A5 片段模板）两者都涉及：数据文件是其**配置值载体**，插件是其**打包加载载体**。**单一落点原则**：某能力若已由数据文件化承载配置值，插件化不再重复建配置落点，只补打包/加载维度。避免双写。

### 4.6 slash 命令通路（补充 P3 遗漏）

**现状**：slash 命令是**独立于扩展包的另一条数据文件化通路**，方案此前未单列。

**设计**：slash 命令单独建 `data/plugins/<id>/commands/` 或 `user/commands.json`，与扩展包/技能型插件并列。在清单中显式标注其独立通路，避免与技能型插件混为一谈。实现时定具体落点。

### 4.7 风险评估（补充 P3 遗漏）

**风险**：AGENT 生成插件无校验——AGENT 可生成任意插件写入 `data/plugins/`，若无校验可能引入无效/恶意插件。

**设计**：
- **加载期校验**：manifest 字段校验 + 权限白名单校验（§4.2/§4.3）。
- **只读扩展面**：插件数据只读消费，不执行用户代码（C4 排除），最坏「没生效」不会「搞坏应用」。
- **告警**：加载失败插件跳过 + 聚合告警，用户可见。

## 5. 分批实施路线

每批一个 OpenSpec change（G0–G4），每批注明按 data-surface 六栏契约落表：

1. **第一批（收尾既有插件形态）**：A1 扩展包 manifest 字段统一 + 权限声明补全；A2/A4 消费方分两类显式区分；B2/B3 统一纳入插件体系登记。
2. **第二批（配置型插件）**：B1 胶囊工具条、B4 菜单、B5 图标、B7 导出配置、B8 阅读预设、B9 新文档默认（与第 2 项数据文件化协同，配置值落点由数据文件承载）。
3. **第三批（技能型与 slash 命令）**：A2 SKILL 注入面拼装细化；B6 键位绑定插件化（依赖第 3 项按键分发层重接线）；slash 命令独立通路落点。
4. **第四批（生命周期与热加载评估）**：插件热加载评估（watcher 基础设施），若成本可接受则补，否则维持重启生效。

## 6. 数据面

本方案触及插件声明、权限、启停等可配置面，按仓库落点契约登记如下。

| 触发信号 | 字段 | 落点 | 默认值 | 消费者 | 可配置性 |
|---|---|---|---|---|---|
| 新增插件能力 / 插件打包 | manifest.json（id/name/version/permissions/type） | `data/plugins/<id>/manifest.json` | 插件自带，无全局默认 | 插件加载管线（`extensions.rs`） | 插件自带声明，宿主校验；用户可启停 |
| 插件启停 / 启用状态 | `plugins.<id>.enabled` | `user/settings.json`（插件段） | 默认关 | 加载管线、设置页 | 用户可开关 |
| 插件权限声明 | `permissions`（如 `filesystem`） | manifest.json 声明 + 宿主白名单 | 无 | 加载时校验 | 插件声明，宿主决定是否接受 |
| 插件自身配置值 | 插件配置键 | 随插件包或 `settings.json` 插件段 | 插件默认值 | 插件运行时 | 用户 / AGENT 可改 |
