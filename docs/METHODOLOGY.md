# Biaoyue 设计工作方法论 — 从 Capture Overlay 复盘

> **版本**: v1.0
> **来源**: Capture Overlay v3.1 → v5.3 全复盘
> **目标**: 标准化需求→设计→验证全流程
> **Ponytail**: meta-process · 模板库 · 评价标准 · 顶层文档 · 交付清单 · 工具集

---

## 零、我们的问题诊断

### Capture Overlay 复盘

| 阶段 | 错误 | 代价 | 根因 |
|------|------|------|------|
| 需求理解 | 把 ASCII 示意图当成最终需求 | v3.1 全部推翻 | 没有 "场景故事" 环节 |
| | Double-Enter 语义读错 | 保存逻辑全错 | 没有 "需求确认清单" |
| | 单行 input vs 多行 textarea | 印哥直接否定 | 没有 "产品调性" 对标 |
| 方案设计 | 3 个分散按钮 | 重新设计 | 没有 "操作成本" 视角 |
| | 无评价体系 | 印哥说 "摸弄" | 没有 "可衡量标准" |
| | 无竞品分析 | 不知道何为好 | 没有 "对标分析" 环节 |
| | 4s undo toast | 删掉白做 | 没有 "误操作成本" 视角 |
| 决策过程 | :问题 命令式 prefix | 印哥否定 | 没有 "心智负荷" 评估 |
| | 向上飞出动画 | 印哥否定 | 没有 "物理隐喻" 分析 |
| 文档质量 | 技术分析为主 | 无法判断效果 | 缺少 "用户故事" + "ASCII 终态" |

### 根本原因

1. **缺少场景驱动**: 没有先回答"谁、什么时间、什么场景、做什么"
2. **缺少评价体系**: 印哥不知道 "好" 的客观标准是什么
3. **缺少分层验证**: 从需求到方案到代码一步到位，没有中间检查点
4. **缺少顶层文档**: 没有纲领性文件作为所有设计的 anchor

### 我们需要什么

- **一份顶层设计文档**: 产品哲学、评价维度、红线规则
- **一套模板**: 需求说明书模板 + 方案设计模板
- **一个流程**: 从需求提出到代码实现的标准化步骤
- **一套评价清单**: pass/fail 标准
- **一份决策追踪**: 为什么选 A 不选 B 的记录

## 一、顶层设计文档 — 纲领

**定位**: 所有设计的最高优先级参考，任何设计不能与其矛盾。

### 文件位置

```
docs/DESIGN-PHILOSOPHY.md        ← Jianxi 整体
docs/capture-OVERLAY-GUIDE.md    ← Capture Overlay 专属 (建议未来写)
```

### 顶层文档应包含

```
一、产品哲学 (一句话)
二、核心原则 (3-5 条)
三、设计红线 (绝对不能违反)
四、评价维度 (5 维度 + 测量方法)
五、竞品参照系 (好/坏的参照)
六、UI 规范 (字体/色/间距优先级)
七、交互规范 (Cmd 优先/Quiet/Feedback)
八、技术决策 (Tauri 2 / Zustand / CSS-only)
```

### 产品哲学一句话

```
Jianxi: 用最少干扰达成用户所愿。
Capture Overlay: 念头出现则录入，录入则离开。中间零仪式。
```

### 核心原则

| 原则 | 含义 | 反面 |
|------|------|------|
| 思路不中断 | 录入过程不打断思维 | 弹出确认/切换窗口/改变焦点 |
| 思维不打扰 | 界面元素不在用户忙时呼叫 | hover/toast/常驻按钮 |
| 误操作可撤销 | 必须有回退路径 | 删除不可恢复 |
| 单一职责 | overlay 只做捕获 | 不做编辑/转正/搜索 |
| 极简视觉 | 输入时界面几乎不存在 | 工具栏/标题栏常驻 |

### 设计红线

- ❌ 不允许常驻 3+ 按钮
- ❌ 不允许输入区上方 > 1 行辅助信息
- ❌ 不允许保存数据丢失
- ❌ 不允许视觉噪声 > 2 级 (主产品是 3 级)
- ❌ 不允许与主产品视觉语言冲突

### 评价维度

| 维度 | 方法 | 标准 |
|------|------|------|
| Capture Latency | 念头→开始输入时间 | < 500ms P50 |
| Actions per Capture | 完成任务的手部操作数 | < 3 次 |
| 误操作率 | 自报误操作/天 | < 1 次/天 |
| 发现力 | 用户 5s 内找到入口的比例 | > 90% |
| 恢复摩擦 | 回到原任务的时间 | < 1.5s |

### 竞品参照系

| 竞品 | 好 | 坏 |
|------|---|----|
| Apple Notes | 极简输入/新建即保存 | 关闭需点"完成" |
| Drafts | Inbox 心态/Action 链 | UI 过载 |
| Google Keep | 打开即写/快捷至上 | 仪式感缺失/广告 |
| Quiet (本产品) | 绝对安静/零按钮 | 需要 hover 学习成本 |

## 四、完整工作流程

### Phase 0: 需求提出 (印哥 → 设计师)

**输出**: `REQ-<功能名>-vN.md`

印哥:
- 按"需求说明书模板"填写
- 至少 3 个场景
- 至少标注 P0 诉求
- 标注开放问题 (不确定的地方)

设计师:
- 阅读 REQ
- 找出歧义和未覆盖的场景
- 与印哥同步确认 (不超过 30 分钟讨论)

**通过条件**: 双方对场景 + P0 诉求 + 验收标准达成一致。

### Phase 1: 方案设计 (设计师主导)

**输出**: `<功能名>-v<N>.md`

设计师:
1. 读取 REQ + 顶层文档 + 相关 spec
2. 列出 3-5 个候选方案 (每个 50 字)
3. 选主推 + 1 个备选
4. 按"方案设计模板"写出 v1
5. 自检通过: 覆盖所有场景 + 评价清单全部可 pass/fail

设计师发给印哥:
- v1 全文
- "主推 vs 备选" 的一段对比
- 标注最希望印哥回应的 3 个决策点

### Phase 2: 3 轮碰撞 (设计师 + Codex)

设计师:
- 用 delegate_task 派 3 个 Codex subagent
- 每轮 focusing on 不同角度
- 收集反馈 → 合并 → v1.1

**碰撞不要重复** — 每轮必须有新的切入点

| 轮次  | 焦点                    |
| --- | --------------------- |
| R1  | 多场景覆盖 + 核心交互 + 竞品对标   |
| R2  | 键盘覆盖 + 误操作保护 + 状态机完整性 |
| R3  | 性能边界 + 多端兼容 + 未来扩展性   |

设计师: v1.1 输出 → codex 验证 (1 轮快速校验) → v1.2

### Phase 3: 决策点集中 (设计师 → 印哥)

设计师提取 ≥ 4 个**无法自己判断**的决策点:

```
C1: [问题描述]
- A: [选项]  优点: ... 缺点: ...
- B: [选项]  优点: ... 缺点: ...
- 设计师推荐: [A/B] 原因: ...
```

印哥确认 C1-Cn → v1.3 定稿

### Phase 4: 实现规格 (设计师)

**输出**: `<功能名>-SPEC.md` (实施规格书)

```
一、新增文件列表
二、修改文件列表
三、每个文件的 API/接口签名
四、状态机的代码映射
五、测试用例 (E2E 验收用)
```

### Phase 5: 代码实现 + 验收 (设计师)

1. 按 SPEC 实施
2. 运行 P0 Checklist: 一项一项过
3. 印哥实测

## 六、评价标准 — 方案好不好的客观衡量

### 6.1 六维评价

| 维度 | 方法 | 方法 | 阈值 |
|------|------|------|------|
| **场景覆盖** | REQ 中的场景是否全部有对应的设计 | 逐场景查 | 100% |
| **操作经济性** | 核心任务的按键+点击数 | 测量 | < 3 次 |
| **误操作保护** | 每个破坏性操作是否有回退路径 | 逐操作查 | 100% |
| **视觉噪声** | 默认态可见的 UI 元素个数 | 数 | < 5 个 |
| **可衡量性** | 每条 Checklist 是否 pass/fail 可测 | 逐项查 | 100% |
| **扩展性** | P2 功能是否预留了设计空间 | 评审 | 不阻塞 |

### 6.2 评价工具

| 工具 | 用途 | 何时用 |
|------|------|--------|
| P0 Checklist | 验收 | 方案定稿前 |
| 决策追踪表 | 记录 "为什么选 A" | 每轮碰撞后 |
| 场景矩阵 | 场景 × 方案覆盖检查 | Phase 1 → Phase 2 |
| 竞品对比表 | 行业对标 | Phase 1 |
| 代码实现映射 | 设计 → 代码的追踪 | Phase 4 |

## 八、Capture Overlay 回看 — 用方法论重新评估

### v3.1 失败的原因

| 阶段 | 理想流程 | 实际 |
|------|---------|------|
| Phase 0 | 印哥写 REQ，3+ 场景 | ❌ 我没有要求 REQ，直接动 spec |
| Phase 1 | 设计师出 v1 方案 | ❌ 我没有出方案，直接写代码 |
| Phase 2 | 3 轮碰撞 | ❌ 碰撞做了但方案已上市 |
| Phase 3 | 决策点集中 | ❌ 我自行决定所有 topic |

### 如果重来

```
印哥: 6 条反馈 → 整理为 REQ-capture-overlay-v1.md
设计师: 出 v1 方案 → 碰撞 3 轮 → v1.1 → 决策点集中 → v1.3 → SPEC → 代码
总计: 3-5 天 (vs 当前的 2 周来回)
```

## 九、一句话总结

```
顶层标准先行 → 场景驱动需求 → 多版方案迭代 → 决策点集中确认 → 实施规格 + Checklist 验收
```

没有顶层标准 → 每次讨论都要从头建立共识  
没有场景 → 设计偏向技术而非需求  
没有评价标准 → "摸弄" 式迭代  
没有版本存档 → 无法追溯设计演进  
没有 SPEC → 代码与文档不同步
