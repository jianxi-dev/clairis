# 软著申请操作手册

Clairis（渐晰）软件著作权登记申请的**操作手册**：申请主体核实、申请表字段映射、日期逻辑校验、常见补正原因与预案、提交前自查清单。配套材料见 [软著资料台账](./ledger.md) 与 [交付路线图](../roadmap.md)；工具配置见 `scripts/softcopyright/config.json`。

> ⚠️ **本手册不填写具体申请日期**：申请时机由维护者按路线图 Phase R（Release 1.0 稳定版发布）完成节点自行决定，手册只提供校验与自查方法，不替用户决定申请时间。

---

## 一、申请主体

### 1.1 主体确定

- **申请名义**：个体工商户经营者**个人名义**申请（用户已确认"以个人名义申请"）。
- **著作权人**：申请人本人姓名（与经营者身份证件姓名完全一致）。
- **理由（与商标主体一致）**：Clairis 商标注册主体为**个体工商户**（经营者个人），以经营者个人名义申请软件著作权，可使软件权属主体与商标权人主体一致，避免"商标归个体工商户、软著归他人/公司"造成的权属主体分裂；后续授权许可、维权、转让时权利链条清晰，无需额外的主体间权利转让手续。

### 1.2 申请前到版权中心官网核实（必做）

申请前登录**中国版权保护中心官网**（版权登记系统），逐项核实个人申请材料要求。2026 年个人申请须完成**电子实名认证**。核实点与操作步骤：

| 核实点 | 2026 现状 | 操作步骤 |
|---|---|---|
| 电子实名认证 | 个人申请须先实名认证 | ① 官网注册个人账号 → ② 进入实名认证流程 → ③ 按提示上传身份证件并完成人脸核验 → ④ 系统审核通过后账号方可发起登记申请 |
| 身份证材料 | 身份证正反面 | 实名认证时上传身份证正反面照片/扫描件，须清晰、四角完整、无反光 |
| 申请表签名 | 线上填报 + 签名 | 实名认证后，系统内申请表由本人**手抄/签署承诺**（手写签名或按系统提示的电子签署方式完成），无需线下纸质签名扫描件（以官网当前要求为准） |
| 承诺书 | 实名后系统内签署 | 按系统提示手抄/签署"申请材料真实、原创"承诺，抄写内容与提示原文一致 |
| 其他个人材料 | 视当前要求 | 以官网"登记指南/材料清单"页为准，逐一比对，避免按旧资料误备 |

> **操作顺序提醒**：实名认证未通过前无法发起申请。建议提前完成实名认证（认证审核需要时间），再准备其余材料。

## 二、申请表字段映射表

字段取值统一取自 `scripts/softcopyright/config.json`（唯一配置源）。**申请前先定稿 config.json 再填报申请表**。

| 申请表字段 | 填写值 | 来源/依据 |
|---|---|---|
| 软件全称 | `Clairis 渐晰阅读编辑软件` | `config.json.softwareName`（申请前定稿；命名规范：品牌号+核心功能+后缀） |
| 软件简称 | `Clairis 渐晰` | `config.json.softwareShortName` |
| 版本号 | `V1.0` | `config.json.version`（首次登记取 V1.0，与路线图 Phase R 对齐；非 1.0 首登可能被要求提供升级说明） |
| 开发方式 | 独立开发 | 自有代码开发，非合作/委托/单位任务 |
| 著作权人 | 申请人本人姓名 | `config.json.ownerName`（**申请前填写**，绝不写入占位空串） |
| 权利取得方式 | 原始取得 | 自主研发取得，非受让/继承 |
| 开发完成日期 | 取自 git 证据链（见下方"取证方法"） | 开发完成 ≤ 首次发表 ≤ 申请日 |
| 首次发表日期 | 取自 GitHub Release / 里程碑记录 | 未公开发布则填"未发表" |
| 开发环境 | Vite + CodeMirror 6 + React 18 + Tauri 2 + Rust | 技术栈事实（`src/` 前端 + `src-tauri/` 后端） |

### 开发完成日期与首次发表日期取证方法

| 锚点 | 取证方法 | 命令/位置 |
|---|---|---|
| 开发完成日期 | git 历史中**最早提交日期**（起算锚）与里程碑 `v1.0.0` tag 日期（完成锚），以里程碑 tag 日期为开发完成日期 | `git log --reverse --format="%ad %s" --date=short \| head`；`git log -1 --format="%ad" --date=short v1.0.0` |
| 首次发表日期 | GitHub Release 发布页日期；无公开则填"未发表" | GitHub Release 页（R 级期创建） |
| 交叉复核 | 里程碑记录表（台账/路线图） | `docs/delivery/roadmap.md`、软著台账 [ledger.md](./ledger.md) |

## 三、日期逻辑校验

### 3.1 核心链式约束

```
开发完成日期 ≤ 首次发表日期 ≤ 申请日
```

同时：**开发完成日期须晚于主体成立日期**（个体工商户成立时间 / 个人主体认定的起算时间，若早于则日期链非法）。

### 3.2 非法组合与检查方法（可执行）

| 非法组合 | 问题 | 检查命令/方法 |
|---|---|---|
| 开发完成日期 晚于 首次发表日期 | 未完成就"发表"，逻辑矛盾 | 对比 `git log -1 v1.0.0` 日期与 GitHub Release 日期；脚本/人工断言 `dev_date <= pub_date` |
| 首次发表日期 晚于 申请日 | 登记的是尚未发生的事件 | 填报前确认发表日在今天之前（`date +%Y-%m-%d` 对比） |
| 开发完成日期 晚于 申请日 | 未完成即申请，会被要求补正 | 同上对比 |
| 开发完成日期 早于 主体成立日期 | 主体尚未存在即"开发完成" | 与个体工商户注册成立日期对比 |
| 首次发表日期 早于 开发完成日期 且差距异常 | 疑似虚构发表记录 | 与 git 里程碑时间线交叉核对 |

### 3.3 检查步骤（每次填报前执行）

1. `git log -1 --format="%ad" --date=short v1.0.0` 取出开发完成日期锚点。
2. 核对 GitHub Release `v1.0.0` 发布日期（或确认"未发表"）。
3. 用系统当前日期确认申请日在发表日之后。
4. 与主体成立日期对比，确认开发完成日期在主体成立之后。
5. 全部满足 `开发完成 ≤ 首次发表 ≤ 申请日` 且 `主体成立 < 开发完成` 才可填报。

## 四、常见补正原因与预案

版权中心发出补正通知后，按下列预案定位原因并处理。**补正次数累计 ≤2 次，超过即驳回、需重新申请**，因此首轮提交前务必跑完第五节自查清单。

| 补正原因 | 处理动作 |
|---|---|
| 页眉软件名称/版本号不一致 | 检查源代码文档、说明书、申请表三处页眉的名称与版本号是否完全一致（见自查清单"三重一致性"）；重新生成源代码文档 PDF（`build-source-doc.mjs`） |
| 截图无软件名称/版本号 | 截图须含软件名称与版本号；用 `capture-screens.mjs` 重新采集（脚本注入覆盖层标注，读取 config.json），替换说明书/材料中的无标注截图 |
| 源代码每页不足 50 行（去空行） | 按 `config.json.linesPerPage=50` 重新分页生成 PDF；空行不计入行数，确认每页有效行 ≥50 |
| 注释占比过高 | 检查源代码文档中注释/空行比例；必要时调整生成参数（注释仍属源代码，但占比过高会被质疑），在独创性说明中解释注释用途 |
| 混入第三方代码 | 严格限定自有代码范围：`sourceRoots` 仅 `src` 与 `src-tauri/src`，`excludeGlobs` 排除测试与构建产物；重新生成 PDF 并核对目录不含框架/库源码 |
| 日期逻辑错误 | 按第三节校验方法重新取证日期，修正后重新提交 |
| 双面打印/纸张格式不符 | 一律**单面打印**，按中心要求的纸张与装订方式提交（以官网要求为准） |
| 查重 >30% | 见下方"查重预案"：提供**独创性说明** |
| 涉及 AI 辅助生成未声明 | 见下方"AI 生成代码声明"：按模板补充声明 |

### 查重预案：独创性说明模板要点

官方查重结果 >30% 时，需随补正提交《独创性说明》。要点：

1. **结论先行**：声明本软件为申请人独立开发完成，源代码文档中复用的部分不构成实质性相似。
2. **复用/参考部分**：逐条列出复用或参考的部分，说明其为**通用框架与常见模式**（如标准库调用方式、常见 UI 布局范式、社区广泛使用的工具函数写法），非他人独创表达。
3. **核心逻辑自研**：说明软件核心逻辑（如 Markdown 解析链路、编辑状态管理、Tauri 桥接、渲染管线）为自研实现，与第三方代码存在实质性差异。
4. **证据支撑**：引用 git 开发记录（中文提交历史、里程碑 tag）作为原创性证据。
5. **措辞**：用事实陈述，不贬损他人软件；不虚构"未参考任何资料"。

### AI 生成代码声明模板

涉及 AI 辅助生成代码时按模板如实声明（2026 新规要求）。要点：

- **工具**：写明使用的 AI 工具名称与版本。
- **用途**：写明 AI 辅助完成的部分（如代码片段生成、重构建议、类型定义、测试辅助）与范围，区分"AI 生成"与"人工编写"。
- **人工审查情况**：写明每一处 AI 生成代码均经申请人人工审查、测试与修改后合入，最终代码的独创性贡献与责任由申请人承担；可引用 `.omo/evidence/` 记录与 git 提交历史作为修改记录证据。
- **声明落款**：申请人签名、日期。

## 五、提交前自查清单

提交前逐项核对，**全部勾选**方可提交：

- [ ] **三重一致性**：申请表 / 说明书 / 源代码文档三处软件名称与版本号完全一致（名称取 `config.json.softwareName`，版本号取 `V1.0`）
- [ ] config.json 已定稿：`softwareName`、`softwareShortName`、`version` 为最终值，`ownerName` 已填写真实姓名（非占位空串）
- [ ] 源代码文档：仅自有代码（`src/`、`src-tauri/src/`），无第三方框架/库源码混入
- [ ] 源代码文档：每页有效行数 ≥50（去空行），总行数与页码范围符合前 30 后 30 / 全量规则
- [ ] 源代码文档页眉：每页含软件名称与版本号，且与申请表、说明书一致
- [ ] 页面编号连续、无缺页，双面打印检查（确认已选单面打印）
- [ ] 说明书：图文并茂、≥10~15 页，截图真实渲染且含软件名称与版本号，无虚构/PS 截图
- [ ] 截图：不包含用户真实文件数据，仅示例/空状态内容
- [ ] 日期逻辑：开发完成 ≤ 首次发表 ≤ 申请日，且开发完成晚于主体成立日期（按第三节方法取证）
- [ ] 开发完成日期与首次发表日期已按 git tag / GitHub Release / 里程碑记录锚定
- [ ] 材料齐全：申请表、身份证正反面、源代码文档、说明书、截图等全部材料就位（按官网清单核对）
- [ ] **开源组件与许可清单**：已如实列出第三方依赖及许可证（由 `package.json` / `Cargo.toml` 核对整理），不遗漏
- [ ] **AI 生成代码声明**：已按模板填写工具、用途、人工审查情况
- [ ] 查重预案已演练：查重报告 + 独创性说明就绪（如需）
- [ ] 输出文件为 PDF 格式，命名规范，文件完好可打开
- [ ] **补正时限**：确认收到补正通知后 **30 日内**提交补正，累计补正 **≤2 次**（超限即驳回、需重新申请）——提交前确认本申请为首轮完整提交，避免因疏漏浪费补正次数
- [ ] 个人信息材料（身份证等）未入库，仅离线/系统内提交
