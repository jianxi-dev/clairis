# 2026-11-25 learnings（#1433 有序列表图标 / 图标类测试盲区）

## 图标名断言是代理属性：`data-icon` 相等不等于字形可区分

现象：#1390 把有序列表手柄的**映射**修回 `OrderListOutlined`，四处测试（`block-handle.test.ts`、`handle-icon-position.spec.ts`、`handle-icon-add.spec.ts`、`ui-fidelity.spec.ts`）全绿；但用户仍看不出有序与无序。真因是 `OrderListOutlined` 字形本身就是「三横条 + 三个 1×2 小竖块」，与 `DisorderListOutlined`「三横条 + 三个 2×2 方块」同构——名字不同，画出来一样。

处置：断言下沉到字形层。单测钉「图标路径 == `ui/icons` 规范字形（SSOT 同源）」+「左缘标记列形状签名：无序 1 种、有序 ≥2 种」；e2e 把真实 DOM 手柄 SVG 栅格化到 canvas，标记列按 y 聚类、每簇 8×8 墨迹签名比对。两层都在旧字形下先红。

判据：QG-4 断言强度阶梯里的「代理属性断言冒充可见行为」（DQ-9 反例类型）。凡是「图标/颜色/形状」类变更，`data-icon` / class 名只算挂载确认，不算验收。

## 原始像素 diff 比例不能当「看起来是否相同」的判据

同一对旧图标，Chromium 栅格化后 raw pixel diff 达 30–33%，差异主要来自横条起点位移（x=5 vs x=8）；按比例阈值判「不同」会放过字形同构的图标。结构签名（左缘标记是否重复同一形状）才是语义判据。

## 回归断言的阈值必须用旧实现标定

单测的标记列阈值最初想用 `start x < 8`，但旧有序字形的横条正好起于 x=5，会把横条算进标记列，使旧字形也得到 2 种签名——测试不再红。最终用 `<5`（排除横条、保留三枚标记）。教训：写完「应该失败」的断言，必须把实现临时改回旧版跑一次，确认它真的红。

## 「映射修复」与「字形修复」是两层，别用一层冒充另一层

#1390 修的是映射正则（`1.` / `1)` 都识别为有序），#1433 修的是字形本身。票面描述「图标还原」时，先问：还原的是**选中哪个图标**，还是**这个图标长什么样**？两层各自需要证据。

# 2026-11-25 learnings（#1437 高亮/裁剪/IME）

## IME 组合期「跳过重建」不能返回旧的 DecorationSet

现象：`createDecorationField.update` 在 `composing && docChanged` 时 `return decos`。用户在正文用 IME 输入几个字后，`@codemirror/view` 的 `TilePointer.advance` 在 `parents.pop()` 抛 `TypeError: Cannot destructure property 'tile' ...`，可见内容从 7511px 塌到 4583px、视频节点 1→0，编辑器不可用。

判据：装饰集只有两种合法状态——按新文档重建，或 `decos.map(tr.changes)` 映射。返回「按旧文档算出的原集合」不是「暂不重建」，是把非法范围交给视图层。修复即映射；`compositionend` 再补一次全量重建。

## 裁剪的 `width` 语义必须只有一个：可见裁剪宽

同一个属性在旧实现里被两处按不同语义读：渲染把 `width` 当可见裁剪宽，`onConfirm` 却保留旧全图宽；于是预览正确、确认后区域错位。正确契约（E-44 本轮修订）：`width/height` = 可见裁剪的显示尺寸，确认时同步写回；无锚点的图片不写宽高，走整图测量路径；拖回整图恢复原锚点。

教训：同一属性在「写入 / 渲染 / 再次进入」三处必须用同一坐标系与同一语义；只修渲染不修写回，会在下一次进入时再次错位。

## 回归用例必须先证明「旧实现下真的红」

#1437 的第一版合成夹具换成正常加载的图片后是**假绿**：修复后的断言过了，旧实现也过。用真实文档二分（逐段裁剪 + 逐个变体）才定位到触发结构——视口内存在加载失败的图片 widget。最终夹具保留「两个 broken 图片 + 标注 + 文末组合输入」，旧实现连跑两次稳定红（同一 TypeError），修复后连跑两次绿。

判据：DQ-3 的「红」不是一句说明，而是一段在旧代码上实际失败的原始输出；夹具不红就换夹具，不换断言。

## 打开卡片改写文档会连锁杀死浮层

`buildCalloutMarkdown` 用 `block.type.toUpperCase()` 重组首行，导致 `> [!highlight]` 打开即被改写成 `> [!HIGHLIGHT]`：一次无意义的文档变更，触发装饰重建，把刚弹出的颜色工具条销毁，用户第一次点颜色按钮看起来「没反应」。

处置：`CalloutBlock` 保存源码原始 token（`typeRaw`），写回原样；类型切换按原 token 大小写风格输出（`[!NOTE]` → `[!TIP]`，`[!note]` → `[!tip]`）。衍生规则：任何「打开即写回」的 widget 都必须保证**无编辑时零 diff**。
